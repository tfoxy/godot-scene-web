### G7o3 — web-export payload staging and rs-core step-transaction cuts (sonnet, rs-increment agent)

After G7o2, GSW's hd-patch is still the one bench input over 0.5·T_p on the g31 (p95 10.64 ms
against 8.51 ms), and the web export on the Rust core still misses hd-patch (12.35 ms). G7o2's own
"next bounded item" named two things: the web export's payload path (it verifies and decodes in
the frame, unlike GSW's since G7o2) and the step transaction's apply/resolve cost (native first).
G7o3 does both. No budget moves (D25, D27), and nothing D31 keeps on the frame path is skipped.

- **Files**:
  - `rs-core-capi/src/core.rs`: `Core::stage(hash, bytes)` (sha256 + decode-check, holds the
    bytes), `unstage`, `verify` (shared with the in-frame path), and `provide` takes a staged
    payload without re-hashing it (consume-once, like GSW's `PayloadStage`) or else verifies in
    the frame as before. `PayloadCounters` (staged, refused, unstaged, provided_staged,
    provided_in_frame, provided_in_frame_bytes) joins `counters()`.
  - `rs-core-capi/src/lib.rs`, `receiver/ext/rs_core_capi.h`, `receiver/ext/rs_core_ext.cpp`:
    `rsc_stage`/`rsc_unstage`, and `apply_timing` (plan, execute, stats, in microseconds, around
    `rsc_apply` / the op stream's `RenderingServer` calls / the stats `Variant` tree).
  - `receiver/rs_rust_applier.gd`: `stage`, `unstage`, `payload_counters`,
    `last_{provide,plan,execute,stats}_us`.
  - `receiver/rs_resource_cache.gd`: a `stager` (an `RsRustApplier`); every arrival path
    (`add_inline`, `add_fetched`, obtain cache/store reads) goes through `_verified()`, which
    stages through the core when a stager is set and otherwise runs the pre-G7o3 GDScript checks
    (same error codes and details either way); eviction and `clear_memory` unstage; `take_verify_us()`.
  - `receiver/receiver.gd`: sabotage `verify-in-frame` (no stager: the pre-G7o3 path); the stager
    is set in `_new_applier` and cleared in `_dispose_applier`; perf histograms `payload_verify_us`
    (outside decode/apply), `provide_us`, `plan_us`, `execute_us`, `stats_us`; opt-in
    `RS_RECEIVER_PERF_SAMPLES=1` writes a per-transaction `samples` array; perf.json gains
    `payloads` (the Rust core's counters).
  - `rs-core/src/apply/mod.rs`, `lower.rs`, `meshes.rs`, `residency.rs`: the step transaction's
    apply/resolve cuts (walk, lower, assemble, classify, resolve), with a counting allocator
    installed in native builds only.
  - `rs-core/src/bin/rs-core-check.rs`: `walk-diff --digests <file>` and `profile`'s
    `accept_allocs`/`apply_allocs`.
  - `gate7-bench.ts`: the `--profile` flag also sets `RS_RECEIVER_PERF_SAMPLES=1` on native and web
    arms, and `--rs-sabotage` now reaches the web arm's `RS_RECEIVER_SABOTAGE` env the same way it
    already reached native and GSW, so `verify-in-frame` can be checked on the web export too.
- **Web-export payload staging.** Mirrors G7o2's GSW change: the web export's fetch completion
  hashes and decodes a payload once it arrives (`receiver.gd`'s fetch path calls `stage`), ahead of
  the transaction that provides it. `provide` consumes the staged entry without re-hashing. A
  transaction whose payload is not staged waits or fails exactly as before. The sabotage
  `verify-in-frame` clears the stager, so `provide` falls back to hashing and decoding inside the
  frame — the pre-G7o3 path, kept reachable for the counters check below.
- **rs-core step-transaction cuts (native and wasm).** Profiling on the g31 (phase timers on)
  showed hd-patch's p95 set by its step transactions (seq 1, 11, …, 101: 11 of 122), each 85–200 µs
  per phase natively. The applier's walk, lower, assemble, classify and resolve phases are cut
  (buffer reuse, fewer allocations, a narrower re-lower). `walk-diff --digests` and `profile`'s
  allocation counters are new `rs-core-check` instrumentation to judge the cuts without a
  regression in the paint digest.
- **Checks**:
  - `cargo test --release` in `rs-core` (37/37) and `rs-core-capi` (8/8, two new:
    `staged_payloads_apply_as_provided_ones`, `corrupted_payload_is_refused_on_arrival`);

    cross-version);
  - `self-test-rs-core.ts --inputs <four bench inputs> --goldens`: the Rust and TypeScript decoders

    pass through the (rebuilt) wasm build too;
  - `rs-core-check walk-diff` on all four bench inputs: the incremental applier's paint digest
    equals an always-walk applier's for every transaction (0 mismatches);
  - `payloads.provided_in_frame == 0` and `staged > 0` on an honest web-rs run; the `verify-in-frame`
    sabotage flips that to `staged == 0`, `provided_in_frame > 0` (checked directly against
    perf.json's `payloads` counters on the desktop web-rs bench, pace-patch);
  - native gates 0–6 under `RS_RECEIVER_CORE=rust` (`receiver/` and `rs-core-capi` changed);
  - every landed `g7-*` group that exists on GSW (file and live) and on the web export on the Rust

#### As built

- **Both payload paths now stage ahead of use.** GSW already did this since G7o2; G7o3 brings the
  web export's fetch-based payload path to the same shape. hd-patch's web-rs arm stages 850
  payloads across 122 transactions and provides every one of them from the stage
  (`provided_staged` 850, `provided_in_frame` 0 on an honest run).
- **Staging alone does not move the web export's frame p95.** A phone profile of hd-patch
  (`--profile`, `dev/g31-web-prof1`) splits a transaction's `apply` as: `execute` (the op stream's
  `RenderingServer` calls) p50/p95 2.15/6.36 ms, `plan` 1.0/2.58 ms, the `provide` loop 0.34/1.08 ms,
  and the stats `Variant` tree 0.34/0.62 ms, against an overall apply p50/p95 of 4.03/9.14 ms.
  **The web export's hd-patch frame p95 is set by the engine's `RenderingServer` calls: `execute`
  is about 6.4 ms of a 9.1 ms apply p95.** That is the next lever, not payload verification or
  decode (1.32/3.07 ms). The same profile put `payload_verify_us` (now off the frame path) at
  p50/p95 1.58/4.47 ms, and measured the g31's wasm software SHA-256 at roughly 14 MB/s (seq 1
  stages 679 KB in 49 ms) — `crypto.subtle` would be native SHA and plausibly 10x+ faster, but it
  only covers the live browser-fetch path and is async, so it is not done here.
- **The rs-core step-transaction cuts hold natively and under wasm.** Per-step-transaction sums on
  hd-patch (seq 11–111, n=11, min over 9 repeats, `provide` excluded): native 3543 → 2733 µs
  (−23%), median 259.9 → 212.3 µs; wasm in Node 5296 → 4106 µs (−22%), median 410.5 → 317.9 µs.
  Per phase (native, wasm about the same): walk −46%, lower −33%, assemble −30%, resolve −20%,
  classify −17%. Allocations per step transaction: apply 639 → 249, accept 299 → 222. No input
  regresses natively or under wasm.
- **GSW's hd-patch p95 falls by about 13%, still a stretch-target miss.** The final interleaved
  g31 run on the merged tip measured 10.71 → 9.33 ms total p95 (every round above 8.51 ms in both
  arms; a pre-merge pair had measured 10.76 → 10.03). The phases that moved are decode
  (2.80 → 2.45 ms p95) and apply (5.58 → 4.68 ms p95); provide, draw and evidence_hash did not.
  Only cheaper *step* transactions move the p95 (G7o2's finding), and the cuts land on 11 of 122
  transactions. The web export's hd-patch stays at 11.7 → 11.8 ms.
- **A flake that is not this increment's.** Live `g7-6` on the web export fails
  `motion-monotonic@web` intermittently on this tree and also on a bundle built from `main`
  (G7u); the pre-G7u bundle passed. Details in results/gate7/g7o3.md.
- **Left for a later increment**: the web export's `provide` loop is still one GDScript call per
  staged hash; a single core call for every staged hash in a transaction (instead of `needed()`
  plus one `provide` per hash) would cut the loop's own overhead, and `execute`'s per-call
  `RenderingServer` cost (which calls the planner issues per step transaction) is unprofiled below
  the aggregate `execute_us` number above. Both are candidates once `rs_calls` lands in the per-
  transaction samples.
