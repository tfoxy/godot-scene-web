# render-stream/12 wire format

Status: **specified and built at PM5** (2026-10-28): the capture emits /12; the C++ encoder, the
TypeScript library and rs-core encode, decode, validate and resolve it, and match `golden-12/`. The receivers accept
/12 and type every particle draw as undrawn until PM6. The governing design is
[particles-multimesh-design.md](particles-multimesh-design.md) ("/12: GPU particles", "Capture
policy", "Headless (dummy) hosts"); "As built (PM5)" below records where the build refined it.
/12 builds on render-stream/11 ([render-stream-11.md](render-stream-11.md)). Like /8 to /11 it is
**opt-in**: nothing below /12 changes, and no default moves ("Opt-in and version policy").

## Why

STS2 draws 1,197 `GPUParticles2D` nodes, every one with a `ParticleProcessMaterial`. After PM2,
most of what is left of the menu's error (about 31 dB) is GPU particles: the menu stars and fog
and the energy counter. Nothing on the host can return the simulated particles (no public
readback; a headless host simulates nothing), so /12 ships the **emitter**: its configuration,
seed, restart and emit events and emission transform, plus the process material it already ships.
Each receiver simulates (PM6). This is the design's **declared approximate tier**
("emitter-exact"): the emitter state is exact and checkable against the hook log; the particle
pixels are not.

**render-stream/12 is render-stream/11 plus exactly:**

1. a new magic (`GRSC`), protocol string (`render-stream/12`), subprotocol (`render-stream.12`) and
   file extension (`.rs12`);
2. the **particles table** (`particles`, and `removed_particles` on a patch), optional keys present
   only when non-empty, right after `removed_multimeshes` and before `shader_time`;
3. an optional transaction key `particle_emits`, the ordered `particles_emit` calls since the base,
   right after `removed_particles`;
4. the `add_particles` command, which replaces /11's `unsupported`/`unsupported-op` lowering of
   `canvas_item_add_particles`;
5. a tenth transaction block, **`pt_f32`** (type `f32`), present **only when non-empty** (it holds
   the particles table's and the emit list's floats);
6. a second shader builtin, **`particle_process_material`**, which makes a `particles`-mode shader
   generated by `ParticleProcessMaterial` `ok`;
7. `features` gains `add_particles` (ops) and `particles` (resources), and
   `observed_unsupported_ops` loses `canvas_item_add_particles`, when the capture plans the
   particles hooks.

Everything else is /11's: framing, the record sha256, canonical JSON, the carried-set rules,
dynamic meshes, multimesh, `content_version`, patched `unsupported`, the hello (under `protocol`
`"render-stream/12"`) and the live transport (W11t's coding included). As with /3 to /11 (memory
`g4e1-rs3-version-switch-pattern`), /12 is not a forked module: `ProtocolVersion::V12` in C++,
TypeScript `version` widens to `2..=12` (the default stays `6`), the Rust `version: u8` likewise,
and every cascade that means "/11 or later" includes /12.

**Why the block is optional.** /11 made every transaction carry all nine blocks. A tenth block on
every /12 transaction would make a /12 stream without particles differ from /11 in every
transaction. With `pt_f32` present only when it holds a float (one spelling per state, as PM1's
optional keys), a /12 stream without particles is transaction-for-transaction what /11 writes, and
differs only in the file header and the session record ("Byte identity with /11").

## File layout

```
magic        8 bytes   47 52 53 43 0D 0A 1A 0A   ("GRSC\r\n\x1a\n")
```

then as /11. Byte 3 is the version as one uppercase hex digit: `C` is 12. A /12 decoder refuses
`GRSB`, and a /11 decoder refuses `GRSC`, both with `bad-magic`. Recording files use `.rs12`.

## Session record

/11's keys and order. When the capture plans the particles hooks (/12 only, all 33 planned):

- `features.ops` gains `add_particles`, `features.resources` gains `particles`, and
  `features.observed_unsupported_ops` loses `canvas_item_add_particles` (each list stays sorted);
- `capture.hooks_planned` gains the 33 hook names ("Calibration").

An `add_particles` command, a `particles` key, a `particle_emits` key or a `pt_f32` block in a
session whose `features.ops` lacks `add_particles` is `meta-schema`.

The texture-format default changes at /12 only ("Curve textures"): `resources.permitted_formats`
then also lists `RF`, `RGF`, `RGBF` and `RGBAF`.

## Particles table

`particles: [<entry>]` (full entries on a full transaction; new-or-differing entries on a patch)
and `removed_particles: [<id>]` (patch only, ascending, ids of the base table, never also listed in
`particles`). Both keys are optional and appear only when non-empty; an empty list under either is
`meta-schema`, either key below /12 is `meta-schema`, `removed_particles` on a full transaction is
`patch-encoding`.

An entry, keys in this order:

```json
{"id":<int>=1>,"origin":"created"|"adopted","status":"ok"|"unsupported"|"freed","reason":null|<reason>,
 "version":<int>=1>,"mode":"2d"|"3d","emitting":<bool>,"amount":<int>=0>,"one_shot":<bool>,
 "fixed_fps":<int>=0>,"interpolate":<bool>,"fractional_delta":<bool>,"local":<bool>,
 "draw_order":"index"|"lifetime"|"reverse_lifetime"|"view_depth",
 "transform_align":"disabled"|"z_billboard"|"y_to_velocity"|"z_billboard_y_to_velocity",
 "trails":<bool>,"trail_poses":<int>=0>,"seed":<int 0..4294967295>,"restarts":<int>=0>,
 "emits":<int>=0>,"process_requests":<int>=0>,"process_material":<material id>|null,
 "draw_passes":[<mesh id>|null, ...],"subemitter":<particles id>|null,"f":<int>|null}
```

- `id` has its own per-session counter from 1, never reused (like meshes and multimeshes).
  `origin` was `"created"` only at PM5 (a pre-arm emitter was unknown, as a pre-arm multimesh is
  at PM1). Since PM7 an emitter that existed before the arm and was adopted at its first draw is
  `"adopted"` ("As built (PM7)"); an `"adopted"` entry in a session that declares no adoption is
  `adoption-entry`, as for every other table.
- The JSON fields are the host's last accepted `particles_*` values, modelled on GLES3's
  `ParticlesStorage::Particles` defaults (`drivers/gles3/storage/particles_storage.h`): at
  `particles_create`, mode `"3d"`, `emitting` false, `amount` 0, `one_shot` false, `fixed_fps` 30,
  `interpolate` true, `fractional_delta` false, `local` false, `draw_order` `"index"`,
  `transform_align` `"disabled"`, `trails` false, `seed` 0, no draw passes, no subemitter, no
  process material; floats as "As built (PM5)" rule 3. `GPUParticles2D` sets every one of them
  in its constructor, so the defaults matter only to a raw-RenderingServer emitter.
- `restarts`, `emits` and `process_requests` count the accepted `particles_restart`,
  `particles_emit` and `particles_request_process_time` calls since `particles_create`.
- `trail_poses` is the length of the last `particles_set_trail_bind_poses` array.
- `draw_passes` has `particles_set_draw_passes`' count of slots; each is the wire id of the mesh
  `particles_set_draw_pass_mesh` set for that pass, or null.
- **Floats** (at `f`, in `pt_f32`), 31 + 12 × `trail_poses` of them:

  | offset | value |
  | ------ | ----- |
  | 0 | `amount_ratio` |
  | 1 | `lifetime` |
  | 2 | `pre_process_time` |
  | 3 | `explosiveness_ratio` |
  | 4 | `randomness_ratio` |
  | 5 | `speed_scale` |
  | 6 | `collision_base_size` |
  | 7 | trail length (`particles_set_trails`' second argument) |
  | 8 | `interp_to_end` |
  | 9 | the last `request_process_time` value (0 before any) |
  | 10–15 | custom AABB: position xyz, size xyz |
  | 16–27 | emission transform, a `Transform3D` in memory order: `basis.rows[0..2]` (xyz each), then `origin` |
  | 28–30 | emitter velocity xyz |
  | 31– | trail bind poses, 12 floats each in the same `Transform3D` order |

  `lifetime`, `pre_process_time` and `speed_scale` are `double` in the RenderingServer API; the
  wire carries them rounded to float32 (round to nearest), and the hook log records the same
  rounding. Everything else is `float` (`real_t`) already.
- **Reasons** (priority order): `particles-3d` (mode 3D in a canvas), `unknown-material`
  (`set_process_material` names a material RID the mirror never saw created), `unknown-mesh` (a
  draw pass mesh the mirror never saw), `unknown-particles` (a subemitter RID the mirror never
  saw). An unknown reference is written as null. An entry stays `unsupported` until the cause is
  replaced by a valid call.
- **Shape rules** (`particles-entry`):
  - `ok`: `reason` null, `mode` `"2d"`, `f` non-null.
  - `unsupported`: `reason` non-null, `f` non-null.
  - `freed`: `reason` null, `f` null, `process_material` null, `draw_passes` `[]`, `subemitter`
    null; the other JSON fields keep their last values.
  - `trail_poses` > 0 needs `trails` true.
- **`version`** starts at 1 at `particles_create` and moves by 1 on every accepted call that
  changes the entry: a JSON field, or a float by bit pattern (so an identical re-set costs
  nothing; `GPUParticles2D` re-sends the emission transform each frame it moves). `restart`,
  `emit` and `request_process_time` always move it (their counters move). `free` moves it. It
  never decreases, and an equal version over a changed entry (a JSON field, or a float by bit
  pattern) is `particles-version`.
- `f` is non-null for every `ok` and `unsupported` entry listed (the floats are 124 B plus trail
  poses, so a listed entry always carries them; an unlisted entry keeps its floats).
- **References** (`particles-ref`, after `mesh-ref` and `multimesh-ref`): every non-null
  `process_material` names an entry of the resolved material table, every non-null draw pass a
  resolved mesh, every non-null `subemitter` a resolved particles entry, and every
  `add_particles` command's `particles` a resolved particles entry (any status, a `freed`
  tombstone included).
- **Publication** (capture): an emitter is in a state's table when an `add_particles` command of
  that state names it, or when a published entry names it (as `subemitter`); a named emitter that is
  freed is a `freed` tombstone while it is still named. A patch lists the entries that are new or
  whose version moved since the base; an entry no command or entry names any more is removed. A
  particles entry's version moving makes the frame publish (like PM1's rule 15).

## The emit list

`particle_emits: [{"particles":<id>,"restarts":<int>=0>,"flags":<int 0..31>,"f":<int>}]`, optional
(present only when non-empty), right after `removed_particles`. Each element is one accepted
`particles_emit` call on an emitter the mirror knows, in call order. `restarts` is the emitter's
`restarts` counter at the call; `flags` is `p_emit_flags`. 23 floats at `f` in `pt_f32`: the
transform (12, the table's `Transform3D` order), velocity (3), colour RGBA (4), custom RGBA (4).

- A patch from base B to target T lists the emits made in host frames (B, T], in call order. A
  full transaction lists only the emits of T's own frame (a joiner does not replay history).
- The capture keeps an append-only emit log with a bounded tail (the last 4,096 emits); a patch
  whose base is older than the tail lists what the tail still holds. `particle-emits`: per
  emitter, the listed count is at most `emits` − the base's `emits` (at most `emits` on a full);
  every `particles` names a resolved `ok` or `unsupported` entry; `restarts` is at most the
  entry's.
- A receiver applies a transaction's particles in this order: each entry's configuration (seed
  included), then `particles_restart` once if `restarts` moved since what it applied, then the
  emits in list order.

## The command

`{"op":"add_particles","particles":<id>,"tex":<id>|null}`: no floats, no `f`. `tex` follows every
/4 op's texture rules.

- An `add_particles` naming a RID the mirror never saw created is
  `{"op":"unsupported","name":"canvas_item_add_particles","reason":"unknown-particles"}` in place,
  with its item-level entry `{"op":"canvas_item_add_particles","item":<id>,"reason":"unknown-particles"}`.
- One naming an `unsupported` emitter stays `add_particles` and adds the derived item-level entry
  `{"op":"canvas_item_add_particles","item":<id>,"reason":"unsupported-particles"}`; a `freed`
  tombstone adds none.
- Below /12, and at /12 without the hooks planned, the command is /11's
  `unsupported`/`unsupported-op`. A /11 connection of a /12 host sees /11's lowering and /11's
  features, with `content_version`s digested over the lowered list (PM1 rule 8's pattern).

## The `particle_process_material` builtin

A shader entry's `builtin` may now also be:

```json
{"kind":"particle_process_material",
 "emission_shape":"point"|"sphere"|"sphere_surface"|"box"|"points"|"directed_points"|"ring",
 "particle_flags":[<"align_y_to_velocity"|"rotate_y"|"disable_z"|"damping_as_friction">...],
 "textures":[<param>...],
 "color_ramp":<bool>,"color_initial_ramp":<bool>,"alpha_curve":<bool>,"emission_curve":<bool>,
 "velocity_limit_curve":<bool>,"orbit_velocity_curve_xyz":<bool>,"emission_color_texture":<bool>,
 "sub_emitter":"disabled"|"constant"|"at_end"|"at_collision"|"at_start",
 "attractor":<bool>,"collision":"disabled"|"rigid"|"hide_on_contact","collision_scale":<bool>,
 "turbulence":<bool>}
```

- It is `ParticleProcessMaterial::MaterialKey` (`scene/resources/particle_process_material.h`,
  `_compute_key`) spelled out: the parts of the material that live in the generated code, not in
  a uniform, so GSW needs no GLSL parser. `particle_flags` and `textures` list the set bits in
  enum order; `<param>` is the `Parameter` enum's name lowercased without `PARAM_`
  (`initial_linear_velocity`, `angular_velocity`, `orbit_velocity`, `linear_accel`,
  `radial_accel`, `tangential_accel`, `damping`, `angle`, `scale`, `hue_variation`, `anim_speed`,
  `anim_offset`, `turb_influence_over_life`, `turb_vel_influence`, `turb_init_displacement`,
  `radial_velocity`, `directional_velocity`, `scale_over_velocity`). `emission_color_texture` is
  the key's `has_emission_color`.
- **Where it comes from.** The capture reads it with the class getters through gate 8's node map
  (G8m): at the frame boundary, for a `particles`-mode shader without a builtin, it takes an
  emitter whose process material uses the shader, a canvas item that draws that emitter, the item's
  node (a `GPUParticles2D`), its `process_material`, and checks that the object is a
  `ParticleProcessMaterial` whose RID is the emitter's material. The generated shader is shared
  per key (`shader_map`), so every material on it has the same key.
- **Effect.** A `particles`-mode shader with this builtin is `ok`: `shader-mode` does not apply,
  and `uses` still lists `time`. Like `canvas_item_material` (D4), the shader policy never withholds
  or excludes its code. A `particles`-mode shader the capture could not key (no node map, a
  hand-written particles shader, a material class other than `ParticleProcessMaterial`) stays
  `unsupported`/`shader-mode`, as below /12.
- Below /12 the builtin is never written: a /11 viewer of a /12 host sees `shader-mode`.
- `builtin-entry` (new): the builtin object has exactly these keys in this order, with these
  spellings; the lists are strictly increasing in enum order; a `particle_process_material`
  builtin on a shader whose `mode` is not `particles` is `builtin-entry`.

## Curve textures

At /12 the capture's default format policy (no `GRC_RESOURCE_FORMATS`) also permits `RF`, `RGF`,
`RGBF` and `RGBAF` for textures **at most 4 rows high**: the one-row `CurveTexture`,
`CurveXYZTexture` and `GradientTexture1D` images process materials name. A taller float texture is
`unsupported-format`, as before. The formats have been legal since /8; this is capture policy, not
a wire change. An explicit `GRC_RESOURCE_FORMATS` is honoured as written at every version.

## Transaction keys and blocks

The transaction keys, in order: `…,"materials",["multimeshes"],["removed_multimeshes"],
["particles"],["removed_particles"],["particle_emits"],["shader_time"],"blocks"`.

Blocks: /11's nine (`item_f32`, `canvas_f32`, `cmd_f32`, `cmd_i32`, `mesh_f32`, `param_f64`,
`backbuffer_f32`, `mesh_u8`, `mm_f32`), always present, then **`pt_f32`** (type `f32`) only when it
holds at least one float. `pt-offset`: over the transaction's `particles` in entry order, each
non-null `f` equals the running float count, then over `particle_emits` in list order; the block's
`count` equals the final total; a float no entry claims, a missing block when one is needed, and
an empty `pt_f32` are `pt-offset`.

## Resolved form

`render-stream-12-resolved/1`: /11's, plus `"particles"` right after `"multimeshes"` when the
table is non-empty. A resolved entry carries the JSON fields (without `f`) plus a `"floats"`
object: `amount_ratio`, `lifetime`, `pre_process_time`, `explosiveness`, `randomness`,
`speed_scale`, `collision_base_size`, `trail_length`, `interp_to_end`, `request_process_time`
(numbers), `custom_aabb` (6), `emission_transform` (12), `emitter_velocity` (3) and `trail_poses`
(a list of 12-float lists). A `freed` entry's `floats` is null. The emit list is per transaction,
not state, so the resolved state does not carry it; the decoded form keeps it verbatim. The
resolved command is `{"op":"add_particles","particles","tex"}`.

## Headless shims (opt-in)

Both follow canvas-texture-headless.md's fence: off by default, armed only on a `headless` display
server (the capture refuses to arm otherwise), engine-free modules a ctest drives.

- **Particles RID shim**, `GRC_HEADLESS_PARTICLES=synthesize`. The dummy's `particles_allocate()`
  returns `RID()`, so every emitter shares the null RID. Armed, the `particles_create` hook replaces
  a `RID()` result with a private RID (`kTag << 32 | (2^31 + n)`, its own tag), so the engine, the
  mirror and the hook log name each emitter by its own identity. A non-null engine result passes
  through, counted. The dummy ignores every `particles_*` call whatever the RID, a canvas command
  stores it unvalidated, and `free` of an unknown RID falls through every owner silently, so frees
  are forwarded. Without the shim, a headless host's emitters are all `RID()`: the mirror cannot
  key them, and every `add_particles` is `unknown-particles` (typed in the hook census).
- **Pre-draw pump**, `GRC_PREDRAW_PUMP=1`. The capture connects its own callable to
  `RenderingServer.frame_pre_draw`, which records that the signal fired this iteration. In the frame
  callback, before the snapshot, if it did not fire (the engine did not call
  `RenderingServer::draw`), the capture emits `frame_pre_draw` itself. Its listeners
  (`CPUParticles2D`'s buffer upload, `AnimatedTexture`) then run, and their calls are stamped with
  this frame and published in its transaction. A rendered host refuses the pump (rule 8 of "As
  built"); `pump_skipped` counts frames in which the engine emitted the signal itself.

Neither is a default. The canvas-texture shim's criterion 5 (a clean exit on the target game) is
the bar each must clear before a product seat uses it.

## Hook log and counters (capture evidence, not wire)

`evidence/resources.jsonl` gains `kind` `"particles"` lines, as PM1's multimesh lines (rule 12):

- one line per hooked `particles_*` call: `call` (the RenderingServer method name; `free` for a
  free of an emitter), `frame` (a call made between frame callbacks F−1 and F, or inside callback F
  before its snapshot, is stamped F and published in transaction F), `rid` (decimal string), `id`
  (wire id, null when unknown), `accepted`, then the call's own arguments under their header names
  (`p_enable` → `enable`, `p_amount` → `amount`, …; a transform as 12 floats in the wire order, an
  AABB as 6, a vector as 3, a colour as 4, a RID as its wire id plus `"<arg>_rid"`; doubles as the
  float32-rounded number the wire carries); `particles_emit` adds `restarts`;
- one `"call":"state"` line per emitter per published frame in which its version moved: every
  entry JSON field (`status`, `reason`, `version`, `mode`, … `subemitter`, without `f`) plus
  `floats` (the entry's 31 + 12·`trail_poses` floats in wire order, null when freed); `rid` is null
  once freed.

`pt-wire` compares every transaction's resolved entries with the newest `state` line at or before
its frame, and its emit list with the `particles_emit` call lines in (B, T]. `counters.json`
gains the 33 hook counts and `captured.particles.<call>` `{mirrored, accepted, changed}`;
`result.json` gains `stream.gate8.particles{live, unknown, builtin_resolved, builtin_unresolved,
pump_fired, pump_skipped, shim_synthesized, shim_engine_allocated}`.

## Opt-in and version policy

| variable | values | effect |
| -------- | ------ | ------ |
| `GRC_STREAM_VERSION` | `6` (default), `8`, `9`, `10`, `11`, `12` | `12` makes file sinks /12, puts `.12` first in the listener's offer and installs the multimesh and particles hooks |
| `GRC_HEADLESS_PARTICLES` | `off` (default), `synthesize` | the particles RID shim |
| `GRC_PREDRAW_PUMP` | `0` (default), `1` | the pre-draw pump |
| `RS_RECEIVER_PROTOCOL` | `…`, `12` | the native receiver and GSW offer `render-stream.12` |

- **Defaults do not move.** File sinks stay /6. The listener offers `.12` only under
  `GRC_STREAM_VERSION=12`, then /11's list. No receiver offers `.12` unless asked. Every /2–/11
  session is byte-identical to what it was; `golden-2/` to `golden-11/` pass unchanged.
- /11's `GRC_MESH_DYNAMIC*` and `GRC_LIVE_CODING` apply at /12 as at /11.
- /12 is unreleased, so increments may still extend it (PM6 adds no wire; a UIT increment adds
  `canvas_item_set_use_identity_transform` at /11, which /12 inherits).

## Receivers (PM5: accept, do not draw)

- rs-core decodes, validates and resolves /12 and exposes `ResolvedState.particles`,
  `Command::Particles { particles, tex }`, `TxDelta.particles_upserted`/`particles_removed`, and
  `Validator::particle_emits()` (the emits of the transaction just accepted, in order, with their
  floats), the way PM1 served multimesh.
- `rs-core-capi` accepts /12 (`VERSIONS` gains 12). Its planner counts each `add_particles` as
  `particles_commands_undrawn` (written only when non-zero) and as an `unsupported_commands` row
  `particles-undrawn`. GSW's executor counts a `particles-undrawn` shortcut. A valid /12 stream
  must never fail a receiver.
- PM6 replaces the counts with the engine replay (native, web: PM6a, "As built (PM6a)") and the
  simulation (GSW: PM6b).

## Global coordinates and `canvas_item_set_use_identity_transform`

Unlike `CPUParticles2D` (PM2 rule 8), `GPUParticles2D` never calls
`set_canvas_item_use_identity_transform`. A global-coordinate emitter
(`local_coords = false`) sends its node's global transform as the emission transform
(`gpu_particles_2d.cpp:136-143`), the particles simulate in global space, and the storage maps
them back into the emitter's local space with the inverse emission transform when it fills the
instance buffer (`drivers/gles3/storage/particles_storage.cpp:407-421`; RD likewise). The canvas
item then draws them through its ordinary transform. So global GPU particles depend on the
emission transform (carried at offsets 16–27), **not** on the unhooked identity-transform call;
the UIT increment is needed for `CPUParticles2D` only.

## Byte identity with /11

- Below /12, every file sink is byte-identical to what it was before PM5 (the particles hooks are
  not even installed).
- At /12, a stream with no particles differs from the same run at /11 only in: the 8-byte magic;
  the session's `protocol`; `features.ops`, `features.resources` and
  `features.observed_unsupported_ops` (rule above); `capture.hooks_planned` (the 33 names);

## As built (PM5): decisions

PM5 built /12 in the capture, the three codecs, rs-core-capi, the native receiver and GSW
([results/p3/pm5.md](../results/p3/pm5.md)). Where the sections above left a choice open, or the
build refined them, these rules are now the wire and the capture. They are frozen with /12.

1. **The goldens.** `golden-12/make_golden.py`'s docstring is the exact list of states 22–26 and
   of the 27 invalid vectors (each fails one rule, with the same code in TypeScript and rs-core).
   States 1–21 of every `.rs12` are byte-identical to golden-11's transactions; only the magic and
   the session differ. The generator fills a field a state does not list with a fixed value
   (`fixed_fps` 0, `collision_base_size` 1); these are test data, not the engine's defaults. The
   golden shader's `uses` is `[]`. `golden-12/coding/` is `rs_live_coding_tool`'s output, as
   golden-11's.
2. **Version steps.** A particles entry's `version` may move by more than one between two
   transactions (several accepted changes in a frame, or a base older than the previous snapshot),
   as a multimesh's may. Validators require only that it never decreases and moves with a change.
3. **Create-time defaults** are GLES3's `Particles` struct: `fixed_fps` 30, `interpolate` true,
   `collision_base_size` 0.01, `amount_ratio` 1, `lifetime` 1, `speed_scale` 1, the custom AABB
   (−4, −4, −4, 8, 8, 8), an identity emission transform, and zero elsewhere.
4. **Trail poses need trails.** GLES3 keeps bind poses set while trails are off, but never uses
   them. The capture carries none (`trail_poses` 0, 31 floats) while `trails` is false, and the
   poses return with `trails` true, because the mirror keeps them. So a host can never produce
   `particles-entry`'s trail rule.
5. **The `param-type` refusal was an `Array`.** STS2's engine build (MegaDot 4.5.1.m.12) passes
   two process-material parameters, `particle_flags` and `use_tex_param`, as a plain `Array`
   (330 materials at menu-1 receive both, matching p3-pm.md's 330). Stock 4.5.1 never does. The
   capture's decoder still logs an `Array` as `"array"`/`param-type`, as before, and at /12 only it
   also carries the packed array Godot converts it to for a uniform array: `int32` for bool and
   int elements (in range), `float64`, `vector2/3/4` or `color`. An empty or mixed `Array` stays
   `param-type`. Below /12 nothing changes. The element type STS2 sends is inferred, not yet seen:
   PM7's game leg confirms it.
6. **The builtin needs adoption.** It is resolved through G8m's node map, which only
   `GRC_ADOPT=arm` connects. Without it the resolution never runs (`builtin_unresolved` stays 0),
   and a process-material shader stays `unsupported`/`shader-mode`. g8pt's capture legs and the
   product seat (`a8` legs) run adopted. A `GPUParticles2D` created after the arm is mapped by
   `node_added`; one created before it is unknown anyway (rule 9).
7. **Older viewers of a /12 host.** A /11 or /10 connection gets the lowered commands, the older
   features, `shader-mode` process shaders, `param-type` process materials and its own
   `content_version` digests, so its bytes are what they were. It does **not** get /11's texture
   format view: the float-format default (Curve textures) is the host's policy, so that viewer
   sees /12's `permitted_formats` and `ok` float curve textures, which /8 and later accept.
8. **Shims.** `GRC_HEADLESS_PARTICLES` takes `off` (default) or `synthesize`; private RIDs are
   `0x47524350 << 32 | (2^31 + n)` ("GRCP"). `GRC_PREDRAW_PUMP` takes `0` or `1`. Both refuse the
   stream on a non-headless display server (`particles-shim-not-headless`,
   `predraw-pump-not-headless`) and on an invalid value (`particles-shim-invalid`), and the pump
   emits only while the capture is armed. The pump's `emit_signal` uses the optional
   `object_method_bind_call` interface.
9. **No adoption of emitters.** An emitter created before the arm is unknown: its draw is
   `unknown-particles`. STS2's menu emitters exist before an `a8` leg arms, so PM7 needs emitter
   adoption (the `GPUParticles2D` getters, design "Capture policy") before it can measure the menu.
10. **Edge rules.** An emitter whose process material is freed becomes `unknown-material` and its
    version moves. A draw-pass mesh that is freed keeps its mesh-table tombstone while an emitter
    names it, like a multimesh's mesh.
11. **Evidence.** The counters sit at `result.json` `stream.gate8.particles` (beside PM1's
    multimesh block), with `file_stream_version` 12. Hook-log call lines carry PM1's `version`,
    `t_us`, `thread` and `omitted` too; enums are logged as ints (`mode`, `transform_align`,
    `order`), `particles_emit` logs `emit_flags` and then `restarts`; `state` lines have no
    `origin`. `drop-restart` skews only the wire (`restarts`, `version`, the emits' `restarts`);
    the hook log keeps the true values, which is what lets `pt-wire` catch it. Like every hook
    line since HC1, a particles line is formatted only while a `resources.jsonl` is open.
12. **Validator order.** TypeScript runs the particles rules right after the multimesh rules;
    rs-core runs them after `backbuffer-offset` and checks `particles-ref` before the float half of
    `particles-version`. This changes only which code a file with several faults reports; no
    golden vector has more than one.
13. **For PM6** (rs-core): `ResolvedState.particles` (`state::Particles`, `floats:
    Option<ParticleFloats>`, `None` exactly when freed), `Command::Particles { particles, tex }`,
    `TxDelta.particles_upserted`/`particles_removed` (unioned by `TxDelta::merge` for window-2
    folds), `Validator::particle_emits() -> &[ParticleEmit]` (read at accept time), and
    `Shader.process: Option<ProcessBuiltin>`, kept apart from `builtin`. TypeScript:
    `transactionParticles`, `transactionParticleEmits`, `particlesFloatsByName`,
    `particlesFloatsInWireOrder`. The capi counts `particles_commands_undrawn` and an
    `unsupported_commands` row `canvas_item_add_particles`/`particles-undrawn`; `receiver.gd` sums
    it into `applied.json` `w11.particles_undrawn`; GSW's executor counts
    `Shortcut::ParticlesUndrawn`. The process shader is never compiled by a receiver yet: only a
    particles entry names its material, and no item does.

## As built (PM6a): decisions

PM6a makes the native receiver and the web export replay /12 emitters
([results/p3/pm6a.md](../results/p3/pm6a.md)). Nothing changes on the wire, in rs-core or in the
capture. The capi and the C++ shim are shared, so the web export (the same side module for wasm)
needed no code of its own. GSW is PM6b's.

1. **Emits at accept, in the capi.** Inside `rsc_accept`, right after PM2's multimesh buffers, the
   capi copies `Validator::particle_emits()` into a queue (`Core.particle_emits`). Every
   transaction accepted before an apply adds its emits, so a window-2 fold keeps them all, in
   order. The apply consumes the queue; `session()` clears it.
2. **Residency.** An emitter is resident while an item's `add_particles` names it and its entry is
   `ok`, and so is every `ok` subemitter a resident emitter names (transitively). Its process
   material is resident as if an item named it as its own material: the material's shader (a
   `particles` shader with the builtin), its parameters, its curve textures and its host time
   (P3-TM). Its draw-pass meshes are resident like a multimesh's mesh. A process material or mesh
   that is not `ok` is set as `RID()`.
3. **Order.** Emitters that stop being resident are freed after the multimeshes and before the
   shaders and materials (so an emitter never outlives its process material). New emitters are
   made, and every resident emitter is configured, after the materials and before the items.
   `canvas_item_add_particles` is issued in item replay, and an item naming an emitter made or
   freed in this apply replays its content. `dispose()` frees emitters first.
4. **The calls, per resident emitter, in the wire's order** ("The emit list"):
   - after `particles_create`, every setter once; after that, each only when its value differs from
     what the planner last sent (floats by bit pattern, as the wire's `version` rule): `emitting`,
     `one_shot`, `interpolate`, `fractional_delta`, `use_local_coordinates`, `mode`, `amount`,
     `fixed_fps`, `draw_order`, `transform_align`, the eight float setters, `custom_aabb`,
     `emission_transform`, `emitter_velocity`, `trails` (with the trail length), and
     `trail_bind_poses` (only when the wire carries poses: PM5 rule 4);
   - `particles_set_seed` when the seed differs;
   - `particles_set_process_material`, `particles_set_draw_passes` and `_draw_pass_mesh` and
     `particles_set_subemitter`, by the RIDs resident now;
   - `particles_restart` once when `restarts` moved since the last apply. A new emitter starts at
     0, so it restarts once whenever the host's ever did (every `GPUParticles2D` constructor does);
   - `particles_request_process_time` (the entry's last value) when `process_requests` moved. A
     new emitter adopts the counter: a joiner's emitter starts fresh and never replays an old
     request;
   - the queued emits naming it, in order (`particles_emit`, the wire's 23 floats and flags).
     Emits naming an emitter this receiver does not hold are dropped and counted.
5. **`particles_set_seed` is not bound in 4.5.1.** `RenderingServer` declares it a virtual but
   `_bind_methods` never binds it, so no ptrcall reaches it. The shim calls the virtual directly
   at the vtable slot after `particles_set_collision_base_size`'s (the header declares the two in
   that order). The slot is found at the first seed, not hard-coded: the shim ptrcalls two bound
   `(RID, float)` setters, `particles_set_amount_ratio` and `particles_set_collision_base_size`,
   on a stand-in object whose vtable is a table of 640 trampolines that each record their index,
   and requires the two to lie exactly 14 slots apart (the header's distance). That makes it the
   same code on the editor, a release template and wasm (where a member call is a
   `call_indirect` through the same table). If the probe fails, the seed stays unset and stderr
   says so; pt-replay fails on that line.
6. **Opcodes 76-91** (after UIT's 75). `ParticlesCreate`, the generic `ParticlesSetBool`/`SetInt`/`SetFloat`/
   `SetRid` (a `which` operand indexes the shim's bind table: `PT_*` in `ops.rs` and
   `rs_core_capi.h`), `SetSeed`, `SetCustomAabb`, `SetEmissionTransform`, `SetEmitterVelocity`,
   `SetTrails`, `SetTrailBindPoses` (an untyped `Array` of `Transform3D`, which the bind's
   `TypedArray` argument converts), `SetDrawPasses`, `SetDrawPassMesh`, `Restart`, `Emit` and
   `AddParticles`; `OP_COUNT` is 92. Emitter handles share the mesh table (`RidRef::Particles`,
   the mesh kind's word), as multimeshes do. 32 RenderingServer binds (4.5.1 hashes).
7. **Typed skips** (`unsupported_commands` rows): `unknown-particles`, `particles-freed` (a
   `freed` tombstone), `unsupported-particles` (e.g. `particles-3d`), `particles-not-resident`, and
   the texture reasons.
8. **Evidence.** The apply stats carry `particles_resources` (made, freed, setters, seed sets,
   material sets, draw-pass sets, subemitter sets, restarts, process requests, emits, emits
   dropped, drawn and skipped commands) only when one of them is non-zero, so every stream without
   an emitter keeps its stats byte-identical. `receiver.gd` sums them into `applied.json`
   `w11.particles`.
9. **Receiver sabotages** (`RS_RECEIVER_SABOTAGE`): `undrawn-particles` is PM5's planner (every
   `add_particles` counted `particles_commands_undrawn`/`particles-undrawn`, no emitter made: the
   "pre-PM6 receiver"); `ignore-particle-emits` replays the emitters but drops every emit (counted
   `emits_dropped`); `drop-particles-restart` never issues `particles_restart` (unit-tested only).
10. **What GLES3 does with it.** `gl_compatibility` (both the fixture's host and the receivers)
    ignores `particles_emit` and `particles_set_subemitter` (`particles_storage.cpp:370-378`) and
    draws no trails (`:301-310`). The receiver issues the calls anyway, so a Forward+ receiver
    would honour them; on GLES3 pixels cannot see an emit, which is why the emit sabotage is judged
    on the replay counts (`pt-replay`), not on pixels.
11. **Pacing.** The particles simulate on the receiver's own clock (`get_frame_delta_time()`), one
    transaction a frame. With `--fixed-fps 60` on both sides the native receiver's pixels equal
    the unarmed reference exactly at every shot (pt-lockstep, informational). Without it a native
    receiver that draws faster than real time runs its particles slow (the first PM6a run: D_ONESHOT
    still lit one lifetime after its restart). So every g8pt receiver leg runs `--fixed-fps 60`,
    and g7-8's web half passes the native leg's engine arguments through, `--fixed-fps` included.

## As built (PM6b): decisions

PM6b makes GSW draw /12 emitters ([results/p3/pm6b.md](../results/p3/pm6b.md)): the approximate
tier of "What exact means here" in particles-multimesh-design.md. Nothing changes on the wire, in
the capture or in the native and web receivers.

1. **Where the simulation runs.** In the shell, in `packages/effects` (`GodotGpuEmitter`,
   `particles/godot-gpu.ts`): the package that owns portable simulation. It is a port of what
   gl_compatibility does with one emitter, not a mapping onto the CPUParticles2D-shaped
   `ParticleConfig`/`simulateParticles` the design named: GLES3's `update_particles` and
   `_particles_process` (inactivity after `1.2 x lifetime`, pre-process and request steps with
   `while (todo >= 0)`, fixed-fps stepping with the 0.1 s clamp, the one-shot end clearing
   `emitting`), particles.glsl's restart test (phase, cycle, randomness by `hash`,
   explosiveness, fractional delta), the generated `start()` and `process()` of
   `ParticleProcessMaterial`, and particles_copy.glsl (inactive particles collapse, `interpolate`
   adds `velocity x frame_remainder`, global coordinates through the inverse emission
   transform, `lifetime` order rotated at the newest particle). This is the design's
   "Godot-RNG mode": `alt_seed = hash(NUMBER + 1 + RANDOM_SEED)`, then `rand_from_seed` per
   parameter in the generated code's order, so a particle's spawn values are the host's to float
   precision. `simulateParticles` is unchanged.
2. **The shell's message.** rs-core `apply/particles.rs` `describe` (gsw-rs `particles_sync`) lists
   every `ok` 2D emitter of the resolved table: the entry's JSON fields and floats, and its
   process material's builtin key, uniforms (scalars and vectors by uniform name) and curve
   textures. An emitter or material is listed only when its version (or, for a material, the
   number of its curve textures resolved) moved since the last call; an empty string means
   nothing did.
3. **Curve textures at their values.** A float payload at most 4 rows high keeps its f32 texels
   beside the RGBA8 quantization (`TexturePixels::floats`), and a half payload its halves, so
   a curve above 1 (a scale curve to 2) is sampled as stored. Sampling is `texture()`'s: linear,
   clamp to edge, at `vec2(t)`.
4. **Order, per emitter, PM6a rule 4's:** the setters (`emitting` only when the wire's value
   moved), the seed, one restart when `restarts` moved, one process request when
   `process_requests` moved. A new emitter restarts once when the host's ever did and adopts the
   request counter. A restart also re-asserts the wire's `emitting`, because
   `GPUParticles2D::restart()` calls `particles_set_emitting(true)` after `particles_restart`,
   and the mirror never sees that call when the value did not change.
5. **The clock.** Each apply steps every emitter once, by the host's shader time delta since the
   previous apply (the process shader `uses` `time`, so a /12 stream with an emitter carries
   `shader_time`). A window-2 fold steps once by the fold's delta; a wrap steps 1/60 s; with no
   shader time, 1/60 s. So the simulation follows the host's frames, not the browser's.
6. **The draw.** `add_particles` lowers as GLES3's TYPE_PARTICLES: draw pass 0's mesh, surface
   by surface, `amount` instances from the shell's buffer (16 floats each, PM3's 2D multimesh
   layout with colours and custom data, half-rounded under gl_compatibility like a multimesh's),
   culled by the custom AABB. An inactive emitter's buffer is zeros (nothing drawn), uploaded
   once. An emitter that is unknown, freed, unsupported, 3D, without a draw pass mesh, or with no
   buffer yet is typed `particles-unavailable-skipped`; an item re-lowers when an emitter's draw
   pass mesh moves or its buffer first appears.
7. **Emits.** gl_compatibility ignores `particles_emit` and sub-emitters (PM6a rule 10), so GSW
   consumes the wire's emits as a counted no-op (`emits`); under the receiver sabotage
   `ignore-particle-emits` they are `emits_dropped`. Trails: gl_compatibility draws none and
   neither does GSW (the trail draw pass mesh is drawn as is).
8. **Not modelled, typed in `approximate_features`:** turbulence's curl noise (its random draws
   are consumed), the `points`/`directed_points` emission textures, `reverse_lifetime` and
   `view_depth` sorting, attractors and collision. An emitter whose material has no builtin key
   is not simulated (`unsimulated`), and its draw is `particles-unavailable-skipped`.
9. **Evidence.** applied.json `w11.particles` (only when non-zero): the wasm's
   `particles_commands`, `skipped_particles_commands`, `particles_commands_undrawn`, `emits`,
   `emits_dropped`, `buffer_sets`, `buffers_held`, `buffers_dropped`, and the shell's
   `particles_created`, `particles_freed`, `restarts`, `seed_sets`, `process_requests`,
   `sim_steps`, `unsimulated`, `approximate_features`. A stream without an emitter is
   byte-identical in evidence.
10. **Receiver sabotages** on PM6a's names: `undrawn-particles` (every `add_particles` counted
    `particles-undrawn`, the pre-PM6b executor) and `ignore-particle-emits`.

## As built (PM7): decisions

PM7 adopts the GPU emitters that exist before a late arm
([results/p3/pm7.md](../results/p3/pm7.md)). Before it, every draw of such an emitter was
`unknown-particles` (PM5 rule 9), so an STS2 arm after the main menu existed could not show the
menu's stars and fog. The capture, the two validators and the hook log change; the receivers
(native, web and GSW) do not: none reads `origin`.

1. **The wire.** `origin` may be `"adopted"` on a particles entry (TypeScript and rs-core accept
   it at /12; `adoption-entry` covers the particles table too). Nothing else changes: an adopted
   entry has the same keys, rules and floats as a created one, and a stream without a pre-arm
   emitter is byte-identical to PM6a's. This relaxes a /12 rule, so it stays /12 (no other
   version carries particles).
2. **When.** An emitter is adopted lazily, at its first `canvas_item_add_particles` after the arm
   (GRC_ADOPT=arm, main thread only), before the command is recorded, so the command names the
   adopted entry and no transaction ever carries its `unknown-particles`. The walk's
   `queue_redraw()` on every adopted item makes that draw at the arm's flush for every visible
   emitter; a pre-arm emitter whose node enters the tree later draws on entry (mapped by
   `node_added`); a hidden one is adopted when it is first shown.
3. **The RID and the mesh come from the draw.** `GPUParticles2D` exposes neither its particles RID
   nor its draw-pass quad mesh. Its `NOTIFICATION_DRAW` (gpu_particles_2d.cpp:602-725) rebuilds
   the quad (`mesh_clear`, `mesh_add_surface_from_arrays`), sets the trail bind poses, then
   calls `canvas_item_add_particles(item, particles, texture)`. The `trail_bind_poses` hook notes
   an emitter the mirror does not know, with the mesh the thread's last `mesh_add_surface` filled
   and the poses; the `add_particles` hook adopts it when the RID matches that note and the
   item's node (G8m's node map) is a `GPUParticles2D`. The mesh is adopted through G8r
   (`adopt_mesh_ref`, the server's read-back of the quad just built). A draw that does not match
   stays `unknown-particles`, counted (`refused_no_node`, `refused_not_gpu`, `refused_no_draw`).
4. **The configuration is the node's getters**, as its setters declared them to the server:
   mode 2D; `emitting` (the node's: a finished one-shot is `false`); `amount`, `one_shot`,
   `fixed_fps`, `interpolate`, `fractional_delta`, `local_coords`, `draw_order`, `seed`; trails
   and `transform_align` Y-to-velocity with them; the floats `amount_ratio`, `lifetime`,
   `pre_process_time`, `explosiveness`, `randomness`, `speed_scale` (0 when the node cannot
   process, as ENTER_TREE sends), `collision_base_size` (scaled by the texture as
   `_update_collision_size`), the trail length (0 without trails), `interp_to_end`, the custom
   AABB from `visibility_rect`, and the global transform as the emission transform. What no
   getter returns starts at the defaults: `restarts` 1 (the constructor's restart: a joiner's
   emitter starts fresh, PM6a rule 4), `emits` and `process_requests` 0, the last
   `request_process_time` 0, emitter velocity 0. A local-coordinates emitter's host emission
   transform is the one of its first transform flush, which can differ from the adopted global
   transform; GLES3 reads it only for emits and subemitters.
5. **The subemitter** is the node `get_sub_emitter()` names (a `GPUParticles2D` other than the
   emitter). Adopted first, it is named at once; adopted later, the parent is linked then, as
   `particles_set_subemitter` would have (a hook-log line `particles_adopt_subemitter`).
6. **A pre-arm process material.** A `ShaderMaterial` or `CanvasItemMaterial` takes G8m's recipe.
   A `ParticleProcessMaterial` has no getter for its shader: the capture makes a duplicate
   (`Resource.duplicate(false)`, the same key) inside `hooks_internal_begin/end`, and the
   duplicate's `get_rid()` (which runs `_update_shader`, particle_process_material.cpp:1866) sets
   the shared shader on the duplicate's own material through the hooks (`material_set_shader`,
   or `material_create_from_shader` for a build whose material makes its RID lazily), which hand
   back the shader RID and every parameter name the constructor and the copy sent; nothing of
   the temporary reaches the mirror, the hook log or `counters.json` (its destructor's
   `material_set_shader(material, RID())` is ignored). The original's code and values come from
   the server: `RenderingServer.shader_get_code`, then `material_get_param` for each of those
   names and each uniform the code declares (unset ones read NIL and are skipped). GLES3 and RD
   keep both; the headless dummy keeps neither, so a headless capture leaves the material
   `unknown-material` (`ppm_refused_code`). An engine build whose `ParticleProcessMaterial`
   assigns its shader outside `get_rid()` names none to the temporary (`ppm_refused_no_shader`):
   its emitters are adopted `unsupported`/`unknown-material`, as before PM7 they were
   `unknown-particles` (results/p3/pm7.md: MegaDot 4.5.1.m.12 does this). The builtin is then
   keyed at the frame boundary as for any process shader (PM5 rule 6).
7. **Evidence.** `result.json` `stream.gate8.particles.adoption` (under GRC_ADOPT=arm): emitters,
   the refusals by reason (the process material's too), meshes, process materials, their shaders
   and parameters, other
   materials, subemitter links, `adopt_ns`. The hook log gains a `particles_adopt` line per
   adopted emitter. `counters.json` `captured.array_params` counts every plain-`Array` material
   parameter by name, element types, size and the form carried (the PM5 rule 5 question).
8. **PM5 rule 5, confirmed on the game.** STS2's MegaDot passes `particle_flags` as an `Array` of
   4 `bool` and `use_tex_param` as an `Array` of 18 `bool` (every call of both, counted by
   `captured.array_params`), and its process shader declares `uniform bool particle_flags[...]`
   and `uniform bool use_tex_param[...]`. GLES3 converts a `bool` array uniform's value to
   `PackedInt32Array` (material_storage.cpp `_fill_std140_variant_ubo_value`), which is the
   `int32` form /12 carries. The capture needed no change.
9. **Fault.** `GRC_ADOPT_FAULT=no-particles` adopts no emitter: the pre-PM7 capture, the premise
   of g8pt's late-arm sabotage.
