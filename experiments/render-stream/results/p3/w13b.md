# W13b: render-stream/13 in the capture: file sinks and the listener's offer (2026-10-29)

W13b makes the capture emit render-stream/13 as W13a built it (/12 plus `GRSD`, `predict_check`
and the predicted `mesh_u8`/`mesh_f32`/`mm_f32` under /12's JSON meta; the binary body stays on
hold). Under `GRC_STREAM_VERSION=13` the file sinks write `.rs13` and the listener offers
`render-stream.13` first, then /12's list. Each stream predicts against its own two previous
transactions: one `rs13::Predictor` per live connection (in HC5's `Hub::FormState`, advanced on the
encode thread) and per file lane (advanced in file order, on the writer under HC5's `set_former`).
Lockstep viewers share each /13 coding through the formation memo, whose key gains the
predictor's history. "As built (W13b): capture" in
[render-stream-13.md](../../protocol/render-stream-13.md) is the spec of what was built.

Receivers are not in scope: the Node viewer (`lib/coding-receiver.ts --version 13`, un-predicting
through the TypeScript library) and `rs-core-check` are W13b's receivers. GSW is W13c, the native
receiver and the web export W13d; nothing on the receiver side offers `.13` yet.

## Host cost

**Not the sweep's numbers: the machine stayed at load 5 to 12 all session** (other agents' timing
legs and this increment's own identity runs), so the real-time comparison the brief asks for is
left to the milestone sweep. What was measured, all under that load:

| what | /12 | /13 | where |
| ---- | --: | --: | ----- |
| `rs13::Predictor::encode` alone, capture-scale full size (C++ bench, 300 patches, `quiet.sh exclusive`) | — | p50 **480 µs** as W13a built it, **370 µs** after W13b's two fixes | encode thread, writer thread |
| the same on `pm7-a12-1` (4,955 STS2 transactions, W13a's code) | — | p50 450, mean 318 µs | |
| file lane formation (`end.stats.encode_ns_total` / transaction, patch lane) | 393 to 497 µs | 934 to 1,324 µs | writer thread (HC5) |
| zstd-base coding of a warm patch (median `encode_us`) | 244 µs | 224 µs | encode thread |
| live formation of one /13 coding (`predict.encode_us` / `formed`) | — | 1.3 to 1.7 ms | encode thread |

So /13 formation costs more than /12's on this host, not less as the design projected: the
projection assumed the binary body (no JSON) and counted only the prediction arithmetic. The C++
writer re-parses the meta W13a's `encode_transaction` just wrote and rebuilds every carried body
through per-surface allocations. A perf profile of the encode (capture-scale): the meta's JSON
42 % (the DOM of `meshes` and the validating skip of every other key), block coding 17 %,
memmove 11 %, malloc/free 15 %, `PredictState` copies 5 %. W13b took the two cheap wins (a
non-validating skip of the keys the predictor does not read, on the writer only, whose input is
trusted; `from_chars` for the numbers it does read), −23 %, every golden byte-identical
(`rs13_codec`). The rest wants a typed writer path (the `Meta` from the `Transaction`, no JSON)
and allocation-free body coding, as rs-core's decoder already is (+27 µs for combat): an increment
of its own before W13z, whose "formation no worse than /12" gate it would otherwise fail. The cost
is per coding, not per viewer (lockstep viewers share it), and none of it is on the frame
callback's thread (HC5); the callback itself is unchanged by W13b (one more pointer compare per
job) and was not measured.

## Findings

- **W13a left `hooks_plan` at /12 only.** `hooks.cpp` reads `GRC_STREAM_VERSION` itself and
  matched `"12"` exactly, so a /13 capture planned no back-buffer, multimesh or particles hooks and
  declared those ops unsupported. `w13-file-equiv` caught it at once (the transcoded session's
  `hooks_planned` and `features` differed from the /12 twin's); fixed. Any further version must
  add itself there too.
- **Shared codings re-converge.** The memo compares histories by content when the pointers
  differ, so a viewer that resynced or joined late codes only its full and the patch after it
  itself, then takes the lockstep viewers' coding (and from then on their history pointers): the
  unit test pins exactly two own codings. Pointer identity alone would have kept such a viewer
  coding its own forever.
- **`predict-stale` is invisible on a round-robin fixture.** It predicts from H2 as if it were
  H1; for a unit that did not move between T−2 and T−1 the two are equal and the stale coding is
  the honest one. capture-scale moves 76 of its 187 meshes a frame round robin, so a mesh moved at
  T did not move at T−1, and most patches code alike either way (the host only sends a patch stale
  when its coding differs, so the sabotage waits). Locally it fired late (seq 217, 87); on the
  hosted runner it never fired. The leg now moves every mesh every frame
  (`RS_SCALE_MESH_UPDATES=187`) and fires at frame 120 exactly; `w13-predict-stale-caught` names
  the host's silence. W13c/W13d's `no-predict-reset` legs want the same care: their fixture must
  move a unit across a full.
- **The Node viewer is slower at /13 than at /12** (the TypeScript un-predict and its BigInt
  XXH64): under load 11 the /13 viewers took ~85 transactions of 420 frames where the /12 viewer
  took 169, so few transactions of theirs shared a base with it. `w13-equiv` therefore judges, live,
  both the messages from a common base and the resolved state at every common frame, and asks for
  enough overlap to judge; the strict whole-stream equality is the unit test's.
- **The hello needed nothing new** beyond the subprotocol and the protocol string: /13's hello is
  /12's.

## Deviations

- The `predict-stale` sabotage is a listener sabotage (live only, like `coding-wrong-prefix`): it
  needs a receiver to resync. On files, W13a's `rs-core-check transcode --stale` already produces
  the stale form and every validator rejects it.
- `w13-equiv` live compares the transactions both viewers received from the same base: live acks
  follow the clock, so the two connections are not guaranteed the same frames. The whole-stream
  comparison is the unit test's, where the pacing is deterministic.
- No capi `VERSIONS` 13, no TypeScript `wireVersionOf()` change, no GSW or native change (W13c,
  W13d).

## Notes for W13c and W13d

- **What a /13 host sends:** offer `render-stream.13` and a hello with `"protocol":
  "render-stream/13"` (/12's keys, nothing new). The session is /12's with `GRSD` and
  `render-stream/13`; every transaction carries `predict_check`. W11t's coding works as at /12;
  its base prefix is the base's uncoded **/13** message, so un-predict after W11t's decode.
- **Predict history = every transaction you accept**, in order, including ones you fold or skip at
  apply. A `predict-check` failure applies nothing and resyncs with reason `coding`; drop the
  patches that arrive before the full without un-predicting them (their history is the failed
  one's). `coding-receiver.ts` is a 40-line reference.
- **Live evidence:** `live-summary.json` connections have `predict.{formed, shared, bytes,
  plain_bytes, encode_us, stale_seq}`; a receiver leg can read the host's `stale_seq` to pin the
  sabotaged seq. The host sabotage is `GRC_SABOTAGE=predict-stale GRC_SABOTAGE_FRAME=<f>`
  (`GRC_STREAM_VERSION=13`); `run-gate8.sh run_g8w11_coding13` shows the leg shape.
- **Fixtures with prediction:** `g8w11/scale13/capture` (187 meshes, 76 of them updated a
  frame), `g8w11/mesh13/capture`, `g8pt/headless-shim13` (particles) and
  `g8pt/headless-pump13` (multimesh buffers). Their /12 twins sit beside them, equal after
  transcoding: a receiver's /13 output can be compared with its /12 output frame for frame.
- **Checker reuse:** `fileEquiv()` (validate both ways + twin equality) and `viewersOf()`
  (now version-aware) are exported; `traceDynamic(data, 12)` reads a transcoded recording.
