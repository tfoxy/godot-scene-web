# W13r: render-stream/13's compact residual (2026-10-30)

W13r builds BIN-D's decision ([bin-d.md](bin-d.md)): the three predicted blocks of /13 (`mesh_u8`,
`mesh_f32`, `mm_f32`) carry their W13a coded bytes as zero runs. /13 is not frozen, so this
changes /13 in place, and /12 and below are byte-identical. The normative text is
render-stream-13.md "As built (W13r)". `golden-13/make_golden.py` (`zr_encode`, `zr_decode`) is the
reference.

## What changed

- **The token format.** Each block is a stream of tokens `uvarint zeros, uvarint n, n literal
  bytes`, which together cover the plain length (the descriptor's `count` × width).
  - The form is canonical at a minimum run of 4: every maximal run of 4 or more zero bytes goes
    whole into one token's `zeros`, and every other byte is literal.
  - The record's block length is the stream's. `count` and `predict_check` stay /12's.
  - Two new codes, checked after the meta and before the un-predict. `zr-length` covers a stream
    that does not cover the plain length exactly, and it wins within a block. `zr-noncanonical`
    covers anything else that breaks the form.
  - /12's `block-length` no longer applies to these three blocks.
- **Four implementations, one byte stream:**
  - the Python reference;
  - the C++ writer and reader (`rs13_predict.cpp`). The W13a coding goes into scratch, then one
    SSE2 scan pass (a 32-byte zero mask) writes the tokens into the record;
  - rs-core (`predict.rs`). It expands each block into reused scratch, which the un-predict
    reads. `wire.rs` exempts the three blocks from `block-length`. The capi and `gsw-rs` resync
    on the zero-run codes as they do on `predict-check`;
  - TypeScript (`render-stream-2.ts`): the decoder, the validator and `encodeRs13`.
- **Writer sabotages** `zr-overrun` and `zr-short-run`, in every writer:
  - `make_golden.py` (`to13(zr_sabotage=)`);
  - C++ (`Predictor::zr_overrun` / `zr_short_run`, plus `GRC_SABOTAGE=zr-overrun|zr-short-run` on
    the live host);
  - rs-core (`rs-core-check transcode --zr-sabotage overrun|short-run`);
  - TS (`encodeRs13({zrSabotage})`).
- **Receivers.**
  - `web/gsw-receiver/live.ts` and the native `receiver.gd` resync with reason `coding` on
    `zr-length` and `zr-noncanonical`, as they do on `predict-check`. Before this they would have
    ended the stream.
  - New live legs `native13-zr-overrun` and `gsw13-zr-overrun` (run-gate8 g8w11c) are judged by
    checks `native13-zr-resync` and `gsw13-zr-resync`. Each runs the predict-resync check under the
    host's `zr-overrun`.
- **Goldens.**
  - golden-13 is regenerated: every file except `make_golden.py` changed bytes.
  - The decoded forms equal the previous ones except the records' `offset`, `byte_length` and
    `sha256`, and the end record's `stats`.
  - New `zero-runs.json`: 18 plain buffers with their tokens, and 20 invalid streams with their
    codes.
  - Seven new invalid vectors:
    - `zr-overrun` and `zr-short-run` (the sabotages, seq 1);
    - `zr-truncated` and `zr-trailing` (`zr-length`);
    - `zr-overlong`, `zr-literal-run` and `zr-split-run` (`zr-noncanonical`, on `predict.rs13`
      seq 2).
- **`wire-budget.py bin13`** now reads the zero-run wire. `j13_zr` is the recording itself, checked
  byte for byte, and `j13` is W13a's wire with the runs expanded. `--wire w13a` reads a recording
  made before W13r.

## Cost against BIN-D's prediction

Desktop (Ryzen 5 5500), `pm7-a12-1` combat warm patches, p50. Timing ran under `quiet.sh
exclusive`; the load from other repositories was 3.5–6.

| | before | W13r | BIN-D predicted | W13r bar |
| --- | --: | --: | --: | --: |
| host zstd-3 encode, µs (`bin13-bench zstd`, capture's zstd) | 95.0 | **66.6** | 98.0 → 69.3 | ≤ 75 |
| host zero-run scan, µs (C++ writer, alone) | | **3.77** (p95 4.08) | ~4 fused, 16 naive | ≤ 6 |
| host predictor incl. scan, µs (C++ typed path) | 54.6 | 62.5 | | |
| receiver ruzstd decode, µs (rs-core native, `coded_decode`) | 132.5 | **70.0** | 132.8 → 69.5 | ≤ 80 |
| receiver native `Validator::accept`, µs | 123.3 | 110.6 | | |
| receiver wasm `accept_us` (W13p profile) | 242.0 | **249.8** | | ≤ 243 (missed) |
| coded B a combat patch (W11t) | 6,422 | 6,242 | 6,242 | |
| zstd input a combat patch, raw B | 88,189 | 49,842 | 49,842 | |

- **Host, net.** The writer pays +7.9 µs a combat patch: the scan (3.8) plus coding into scratch
  and copying the tokens out. zstd saves 28.4 µs. That nets **−20 µs a combat frame** on HC5's
  encode thread, inside BIN-D's −13 (naive scan) to −25 (fused) µs.
  - Capture-scale's file lane (`--perf`, no zstd) measures the writer alone: formation 3.28 →
    3.20 M instructions a transaction, the predictor 0.193 → 0.221 M of it (the scan 0.015 M).
    Cycles are too noisy under this load to call (formation 2.50 → 2.68 M; `encode_transaction`
    alone, which W13r does not touch, read 1.55 → 1.71 M).
- **Receiver.** Native ruzstd halves (−62.5 µs), as BIN-D predicted. On the g31 that is about
  −0.8 ms a combat message by BIN-D's 13× scaling.
  - The expand costs 3–4.5 µs natively (`unpredict_record` 16.9 → 21.2 µs on seqs 2288–2600).
  - Native accept still falls, 123.3 → 110.6 µs, because the smaller record hashes faster.
- **The wasm accept bar is missed by 7.8 µs (+3.2 %).** The wasm profile defers the record digest
  (the product client never computes it), so the smaller record does not pay back the expand
  there. The digest itself falls 255 → 145 µs.
  - The receive path as a whole still gains about 75 µs a combat message in wasm: ruzstd's
    −62.5 µs native × W11t's 1.2 wasm ratio, less the 7.8.
  - Two tries did not close the gap: keeping the scratch zeroed and writing only the literals was
    slower, and copying short literals a word at a time gained little.
  - Closing it means an un-predict that reads tokens directly. That is a deep change for 8 µs
    against a 75 µs gain, so it is not done.

## Deviations

- **The scan is not fused into `code_words`**, as the W13r row asks. `code_words` writes each
  unit's words into four byte planes across the whole block, so a block's output order is known
  only when the last unit is written. Instead the writer codes into scratch and runs one SSE2
  scan pass, which takes 3.8 µs against the row's 6 µs bar. The brief allowed this.
- **wasm `accept_us` +7.8 µs over the bar** (above).
- **pm-a11-1 and late-1** are /11 and /8 and are not transcodable; see "Proofs".
- **No real-time leg.** Real-time timing is left to the milestone sweep. The cost table is bench
  numbers.

## Couch coordination

The couch-coop seat streams /13 (couch `7124aa83`), and the page's client core is built from GSW
source. After W13r the seat's capture and the page's client core must come from the same GSW
commit (W13r or later). A mismatch never draws wrong geometry, but it does not recover:

- an old capture with a new page fails `zr-length` on every transaction with a predicted block,
  resyncs, and fails again on the full;
- a new capture with an old page fails `block-length` at framing, a hard stream error.

What the couch side needs, after this commit:

1. **Rebuild the capture:** `scripts/build-render-capture.sh` with `COUCHCOOP_GSW_ROOT` at this
   GSW commit. It writes `.sts2/render-capture/librender_stream_capture.so`.
2. **Rebuild the client package from the same commit:** `build-render-stream-client.sh`, same
   `COUCHCOOP_GSW_ROOT`. Its wasm core is rs-core's `gsw-rs`. The frontend's vite aliases resolve
   GSW TypeScript from `COUCHCOOP_GSW_ROOT` (`frontend/vite.config.ts`), so a dev server picks up
   `live.ts` directly.
3. **The release pin.** `release-dependencies.json` pins godot-scene-web `4578ce1e`. A tagged
   release clones that commit, which predates /13 entirely (W13a is `8bfb9490`). Before a tagged
   release that streams /13, the pin has to move to this commit or later. A `--snapshot` package
   uses the sibling checkout's current commit, so it is unaffected.

Nothing in couch was changed.
