# W13z: render-stream/13 on STS2, the acceptance leg (2026-10-30)

W13z is the "Increments" W13z row of [render-stream-13.md](../../protocol/render-stream-13.md): /13
(W13a's predicted blocks under /12's JSON meta), window 2, W11t coding (zstd-base), GSW and native
viewers, STS2 menu, map and combat. The build is `main` at `83c589b3` (W13p): the capture
`d349f3c6…`, the GSW bundle `rs_core_build sha=83c589b3c65c-dirty` (wasm `19522e9c…`, 2,418,563 B;
"dirty" is only the uncommitted scratch tool below), served on 18751 for the replays.

**Scope (the orchestrator's call, 2026-10-30).** W13z is the acceptance and, if it passes, the
product switch. It does **not** freeze /13. The freeze is a separate step before any release, after
TAG1/TAG2 (item identity, which lands at /13 per
[client-extensions-design.md](../../protocol/client-extensions-design.md)) and the binary-syntax
decision.

## Verdict

/13 meets its network and correctness bars on STS2, and **fails the host-cost bar**. Formation on
HC5's encode thread costs more at /13 than at /12, not less as the design projected. So the
product is **not** switched. The couch-coop switch is ready and tested on the couch branch
`worktree/w13z` (`69a4d912`), but it is not on main. The fix is named under "What fails, and the
fix".

| criterion (W13z row) | measured | verdict |
| --- | --- | --- |
| warm coded bytes within 10 % of the projection | combat **5,992.5 B** a patch (projection 6,171: −2.9 %), **2.88 Mbps** at 60 fps (2.96); map **315.5 B** (332: −5.0 %); menu **390.9 B** (510: −23 %, *below*; see note) | **pass** (menu below the band) |
| replay dB equal to /12's on the same recording | 22 steps × GSW and native: every /13 shot is a byte-identical PNG to the /12 transcode's (table below) | **pass** |
| a /12 and a /13 viewer of one host resolve alike at every shared frame | **18,894** shared frames, **0** differ (state and every multimesh buffer) | **pass** |
| zero `predict-check` errors | 0 on all four /13 connections (GSW, native, Node) and the product page: no failure, no drop, no resync | **pass** |
| host callback + formation no worse than /12 (load-gated, `perf` on the GPU host) | main-thread callback equal within noise; **formation +20–40 % cycles in combat** (+0.44 and +0.94 M cycles a frame, ≈ +0.1–0.25 ms) on the encode thread; the predictor alone takes **190–199 µs** a combat frame, and zstd saves 10–15 % | **fail** |

Menu note: the /12 control on the same frames measured 913 B a patch, 18 % under the projection's
/12 figure (1,120). This menu instance is lighter than `pm7-a12-1`'s. The /13 to /12 ratio is 0.43
here, against 0.46 projected, so the shortfall is the scene's, not /13's.

## The legs (three game launches)

Each launch followed the same rules:

- **Order of locks:** the load gate (< 4) outside every lock, then the couch-coop lease
  (`exclusive:game:p3-sts2`, `shared:install`, own ports), then GSW's quiet lock exclusive.
- **Isolation:** a private farm and XDG, `gamescope --backend headless`, `--force-steam off`,
  `GRC_HOOK_LOG=off`, and nothing written under `~/.steam`.
- **Lifecycle:** every launch ended `survivors: none`, and all five hash sets were unchanged
  (Steam remote, operator profile, install binaries, install mods, mod build).

The exact commands are in `artifacts/render-stream/p3/w13z/harness/`.

1. **`w13z-c3-1`, correctness and bytes.** This launch used C3's GPU host, mode `a13` (new, below):
   capture armed at mod init, `GRC_STREAM_VERSION=13`, file sink `recording-patch.rs13` plus store,
   inline 4096, `GRC_LIVE_MAX_CONNECTIONS=4`. Route menu, map and combat, 72 s each.
   - Four viewers joined at readiness and stayed until the disarm (frame 19,500). Each one ended at
     the end record:
     - GSW at /13 (`RS_RECEIVER_PROTOCOL=13`, window 2);
     - the native receiver at /13;
     - GSW's Node coding viewers at /12 and /13 (`coding-receiver.ts`, which keeps every decoded
       message).
   - Each scene had a 30 s window, bracketed by probe shots that give its frames.
2. **`w13z-c3-2`, host cost.** HCz's table at /13: live only (no file sink, no store),
   `GRC_LIVE_MAX_CONNECTIONS=2`. **One** GSW viewer, whose protocol alternated per window. Each
   window was join, 15 s settle, 30 s measure and 9 s of `perf record -g -F 499`.
   - Route menu, map, combat, map, combat.
   - Window order: menu 13, 12, 13; the first map and combat 13, 12; the second map and combat
     12, 13. That is ABBA per scene within one process.
   - The 1-minute load was 1.0–4.7 in every window, and the host ran 59.2–59.9 fps.
3. **`w13z-mir3-1`, the product seat.** This was MIR-3's harness, with the seat at /13. Its mod was
   built from the couch-coop branch: `StreamingSeatLaunch.StreamVersion = 13`, a descriptor that
   accepts 13, and a page whose client gets `protocol: 13`. The client core was built from GSW
   `83c589b3`.
   - The host was a real co-op host in the `pc-lobby-host` lobby. One page viewer in headless
     chromium-1223 (renderer = stream) joined, and the host launched its seat as the streaming seat.
   - Driving: `act ready` on host and seat, then voting the first map node, which leads to combat.

## Host cost (w13z-c3-2, one viewer, /13 and /12 windows in one process)

### Main thread

This is HCz's split: `perf-capture-split.py`, ms per frame, sample counts at 499 Hz. HCz's
`hcz-c3-2` at /12 measured callback menu 0.26, map 0.25 and combat 1.05 ms.

| scene | /12 windows: hooks + callback | /13 windows: hooks + callback |
| --- | --- | --- |
| menu | 0.164 + **0.291** | 0.109 + **0.270**; 0.171 + **0.289** |
| map | 0.046 + **0.166**; 0.049 + **0.176** | 0.049 + **0.230**; 0.063 + **0.188** |
| combat | 0.471 + **0.961**; 0.541 + **1.185** | 0.491 + **0.973**; 0.593 + **1.487** |

- **The callback is the same within the spread between windows.** The /13 combat window at 1.487
  is the one taken at the highest load (3.1). Its pair, v13-5, reads 0.973 against /12's 0.961.
- **One protocol-dependent item runs on the main thread:** /13's history is released there. The
  hub's predictor states are destroyed in the callback (`rs13::Predictor::~Predictor`, the
  `MeshBodies` map erase, `PredictState` dispose). That is 0.04–0.07 ms a combat frame. The design
  expected only a reference count on the main thread.

### Formation (HC5's encode thread)

Cycles per frame (each sample weighted by its period, M cycles), and the host's own predictor
timer (live-summary `predict.encode_us` ÷ transactions):

| scene | /12 encode thread | **/13 encode thread** | /13: predictor | /13: zstd (vs /12) | predictor timer |
| --- | --: | --: | --: | --: | --: |
| menu | 0.648 | **0.719, 0.748** | 0.133, 0.148 | 0.292, 0.250 (0.370) | 50, 49 µs |
| map | 0.379, 0.365 | **0.500, 0.418** | 0.077, 0.087 | 0.090, 0.113 (0.173, 0.179) | 13, 13 µs |
| combat | 2.114, 2.241 | **2.552, 3.185** | 0.661, 0.837 | 1.077, 1.169 (1.232, 1.304) | **190, 199 µs** |

- **Combat formation costs +20 % and +42 %** in its two A/B pairs. The predictor adds about
  0.75 M cycles a frame, and zstd saves only about 0.15 M.
- **Map and menu** cost +15–32 % and +11–15 %.
- **The `/proc` thread ticks give a smaller gap.** The encode thread's ticks over the 30 s windows
  read combat /13 0.73 against /12 0.72 ms a frame. Tick accounting under-counts a thread that
  wakes once a frame for well under a tick. W13p's warning applies: the cycles and the host's own
  timer are the comparators here.
- **The verdict is a fail.** The design projected formation to *fall*: 0.35 to about 0.2 ms, the
  prediction costing 0.02–0.05 ms and zstd dropping 291 to 90 µs. Live it rises by about 0.15 ms
  in combat.
  - The prediction costs about 4× its projection (190 µs, against W13p's 70 µs p50 over all of
    `pm7-a12-1`).
  - zstd saves 10–15 %, not 69 %, because a /13 message is as large as /12's before coding.

## What fails, and the fix

The name is **W13f**: /13 formation at or below /12's, and no history release on the main thread.
It is a capture-only increment, and the wire stays byte-identical.

1. **Live predictor allocation.** W13p's history reuse (`next_state` refilling the state that leaves
   H2) applies only when the predictor is the state's sole holder. Live, the hub's memo holds every
   coding's resulting history, so live predictors "simply allocate, as before" (W13p). That is the
   likely bulk of the 190 µs a combat frame. To fix it, let the memo hold states weakly, or release
   memo entries before the next formation, so the live path reuses H2 as the file lanes do. Then
   measure it on `pm7-a12-1` through `Hub::form_predicted`, not the file lane.
2. **Release on the encode thread.** Hand the dropped `PredictState`s and predictor copies to the
   encode job, so the callback only decrements a count. That removes 0.04–0.07 ms a combat frame
   from the main thread.
3. **Optional, a wire decision:** a compact residual, eliding zero byte-plane runs, would shrink
   the zstd input as the prototype's layout did (52.7 KB against 88 KB) and recover the projected
   zstd saving. That is a /13 wire change, so it belongs with the binary-syntax decision before the
   freeze, not in W13f.

The acceptance's other criteria hold, so after W13f only the cost leg (`w13z-c3-2`'s command) needs
re-running before the switch lands.
