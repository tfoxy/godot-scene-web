## Gate 7o3 result: web-export payload staging and rs-core step-transaction cuts

Design: [protocol/gate7/g7o3.md](../../protocol/gate7/g7o3.md).

**On the g31, GSW's hd-patch p95 moves from 10.71 to 9.33 ms against 0.5·T_p = 8.51 ms (-13%,
still a miss; `hd` is a stretch target on the g31, D25). The web export on the Rust core does not
move on hd-patch (11.71 -> 11.84 ms, inside the run-to-run band): staging its payloads ahead of
use does not touch its frame p95, because that p95 is set by Godot's `RenderingServer` calls
(`execute`, about 6.4 ms of a 9.1 ms apply p95), not by payload verification or decode.** Every
other bench input (scene-full, scene-patch, pace-patch) passed before this increment and still
passes, on both receivers, before and after.

Two changes:

- The web export now verifies and decodes a resource payload when it arrives (its fetch
  completion), the same way GSW has since G7o2, instead of inside the frame that uses it.
- `rs-core`'s step-transaction phases (walk, lower, assemble, classify, resolve) are cut natively
  first, then measured under wasm: native sums drop 23%, wasm sums drop 22%, with no input
  regressing on either target.

Evidence (ignored): `artifacts/render-stream/gate7/g7o3/` in the G7o3 worktree. The final benches
are `tip-gsw/` and `tip-web/` (run on the merged tip, `rs-core/50bde1f58ea2`, bundle
`web-receiver/a3994d48239b6dd5`); the phone profile is `dev/g31-web-prof1/`. An earlier pair of
benches on the pre-merge tree (GSW 10.76 -> 10.03 ms, web 12.61 -> 12.74 ms on hd-patch) was
superseded by these and deleted; it agreed within noise.

### Where hd-patch's web-export p95 comes from

A phone profile of hd-patch (`--profile`, `dev/g31-web-prof1/`, before vs. this tree) splits a
transaction's `apply` (p50/p95 4.03/9.14 ms) into:

| Phase | p50 / p95 ms |
| --- | --- |
| `execute` (the op stream's `RenderingServer` calls) | 2.15 / 6.36 |
| `plan` (the capi planner) | 1.0 / 2.58 |
| `provide` loop (GDScript, one call per staged hash) | 0.34 / 1.08 |
| stats `Variant` tree | 0.34 / 0.62 |

**`execute` is about 6.4 ms of a 9.1 ms apply p95: the web export's frame cost on hd-patch is set
by the engine's `RenderingServer` calls, not by payload verification or decode.** That is why
staging moved GSW (where `apply` is cheap GDExtension/native call overhead already) but not the
web export (where `RenderingServer` calls themselves dominate). `decode` is 1.32/3.07 ms, unmoved.
`payload_verify_us`, now off the frame path, is 1.58/4.47 ms. The g31's wasm software SHA-256 runs
at roughly 14 MB/s (seq 1 stages 679 KB in 49 ms); `crypto.subtle` would be native SHA and
plausibly 10x+ faster, but it only covers the live browser-fetch path and is async, so it is not
done here. The next lever for the web export's p95 is `execute`, not staging.

### The rs-core step-transaction cuts

Per-step-transaction sums on hd-patch (seq 11–111, n=11, `provide` excluded, min over 9 repeats):

- native: 3543 → 2733 µs (−23%), median 259.9 → 212.3 µs
- wasm in Node: 5296 → 4106 µs (−22%), median 410.5 → 317.9 µs
- per phase (native, wasm about the same): walk −46%, lower −33%, assemble −30%, resolve −20%,
  classify −17%
- allocations per step transaction: apply 639 → 249, accept 299 → 222
- no input regresses, native or wasm; hd-patch p95 native 259.7 → 211.8 µs, wasm 409.7 → 317.6 µs

Correctness: rs-core 37/37, rs-core-capi 6/6 (8/8 after the pick onto this tree), goldens pass,
`walk-diff` 0 mismatches on all four inputs, and for every transaction of all four inputs the paint
digest, packed-list digest and stats (without timings) are identical to `main`'s.

**The `g7-6` web `motion-monotonic` flake is not this increment's.** The check fails a gap of three
frames between applied transactions when the earlier transaction's receipt-to-submitted time was
under one frame (the host or wire is blamed). Four of five runs of this tree's bundle failed it
(different legs each time: live-scene, live-scene-warm, live-stall, a sabotage leg); one passed.
The pre-G7u `main` bundle (`9826704e`) passed twice, but a bundle built from `main` itself
(G7u, `e7c8235f`: `receiver/`, `rs-core` and `rs-core-capi` taken from `main`) failed two of two
the same way, with the same 3-frame gaps whose earlier transaction fetched nothing. So the
check's sensitivity arrived with G7u's web receiver (or its run-to-run phase), not with staging
or the step-transaction cuts. The orchestrator should look at it under G7u / the next sweep;
G7wf's 27/27 g7-6 was before G7u. The rest of live `g7-6` (and every other web check) passes.
